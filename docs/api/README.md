# API кредитного конвейера: памятка для фронтенда

Контракт — `openapi.yaml`: эндпоинты, схемы, статусы, коды ошибок и соглашения о деньгах, датах, `null`, PATCH, ошибках и пагинации. Здесь только то, чего в нём нет.

Бренд интерфейса — Гамма-Банк, продукт для нового бизнеса — «Гамма-Старт».

## Мок без бэкенда

```bash
npx @stoplight/prism-cli@5 mock openapi.yaml
```

Мок работает на `http://localhost:4010` и отвечает примерами из контракта. Отличия от бэкенда:
- пути без `/api/v1`, поэтому базовый адрес лучше держать в переменной окружения;
- подходит любой токен в `Authorization: Bearer`;
- состояние не хранится: после отправки заявки её статус не изменится;
- поток уведомлений не работает, вместо него — `GET /notifications`;
- пример выбирается заголовком `Prefer`. Карточка заявки: `example=approved`, `needInfo`, `preliminary`, `rejected` или `expired`. Вход: `example=client` и `example=underwriter`. Ошибка: `Prefer: code=409`, просроченный оффер: `Prefer: code=409, example=offerExpired`.

## Вход и демо-компании

`POST /auth/demo-login` с `{"role": "CLIENT"}` или `{"role": "UNDERWRITER"}` возвращает токен и пользователя. По `user.role` показываем кабинет клиента или бэк-офис. У демо-клиента шесть компаний, по одной на сценарий:

| Компания | ИНН | demoScenario |
|---|---|---|
| ООО «Северный ветер» | 7841256395 | Одобрение |
| ИП Морозов Дмитрий Олегович | 526218493785 | Ручная проверка |
| ООО «Альтаир» | 6673482158 | Отказ: просрочка |
| ООО «ТехноПром» | 5406217388 | Предварительное одобрение |
| ИП Соколова Анна Викторовна | 165809341759 | Гамма-Старт |
| ООО «Вектор-Строй» | 7724185366 | Отказ: ликвидация |

Компании приходят в `user.companies`. В шапке кабинета клиента — переключатель с подписью **«Демо-режим: выберите компанию»**: название, ИНН и серым `demoScenario`, если оно есть. `companyId` выбранной компании передаём в `POST /products/match`, `POST /applications` и в фильтр `GET /applications?companyId=…`. Без фильтра приходят заявки всех компаний клиента, у каждой есть `companyName`. Компанию у созданной заявки сменить нельзя.

## Подписка и подбор

На карточке продукта две кнопки: «Оформить» и «Оформить с подпиской». Рядом с `baseRate` серым — `rateWithSubscription`, под кнопками — `subscriptionDescription`. Если `rateWithSubscription` нет, вторую кнопку не показываем. Нажатая кнопка задаёт `subscription` при создании заявки. Подбор подписку не принимает и проверяет оба варианта, рекомендованный продукт — первый с `recommended: true`:

| suitable | requiresSubscription | Что показать |
|---|---|---|
| true | false | Продукт подходит, обе кнопки |
| false | true | Только «Оформить с подпиской» и пояснение из `reasons` |
| false | false | Продукт не подходит, причины в `reasons` |

## Кнопки заявки

Кнопки показываем только из `availableActions`, подсказку клиенту берём из `nextStepHint`.

| Действие | Вызов |
|---|---|
| `EDIT` | `PATCH /applications/{id}` |
| `SUBMIT` | `POST /applications/{id}/submit` |
| `CANCEL` | `POST /applications/{id}/cancel` |
| `RESPOND_INFO` | `PATCH` полей, затем `POST /applications/{id}/info-requests/{requestId}/response` |
| `UPLOAD_DOCUMENT` | `POST /applications/{id}/documents` (multipart: `file`, `documentType`), затем `documentIds` в ответе на запрос |
| `ACCEPT_OFFER` | `POST /applications/{id}/offer/accept` |
| `DECLINE_OFFER` | `POST /applications/{id}/offer/decline` |
| `SIGN` | `POST /applications/{id}/signing/request-code`, затем `.../signing/confirm` |

## Основной сценарий клиента
1. Вход через `POST /auth/demo-login` и справочники `GET /dictionaries`, затем клиент выбирает компанию.
2. Клиент отвечает на вопросы подбора, фронт вызывает `POST /products/match` с `companyId`.
3. Клиент нажимает «Оформить» или «Оформить с подпиской», фронт создаёт черновик через `POST /applications`.
4. Анкета заполняется по шагам через `PATCH /applications/{id}`.
5. `POST /applications/{id}/submit`. Пока идёт обработка, опрашиваем `GET /applications/{id}` раз в 2–3 секунды или слушаем `GET /notifications/stream`.
6. При одобрении клиент принимает оффер до `offer.expiresAt` — срок стоит показать на экране.
7. Подписание: `signing/request-code`, на экране показываем `demoCode`, затем `signing/confirm`.
8. Статус `DISBURSED` — экран «Деньги выданы».

## Условия продуктов

Условия демонстрационные — на карточке продукта и оффера стоит пометка «Условия демонстрационные». Ставки, сроки и комиссию за подписку берём из полей продукта и оффера и не хардкодим.

Обязательные поля анкеты:

| Когда | Поля |
|---|---|
| Для отправки (`submit`, иначе 400 по полям в `errors`) | `productCode`, `purpose`, `requestedAmount`, `term` + `termUnit`, `fundingMode` |
| Для решения банка: «Кредит одной суммой», «Кредитная линия» | `financials.annualRevenue`, `financials.annualExpenses`, `financials.monthlyDebtPayment` |
| Для решения банка: «Овердрафт» | те же и `financials.bankMonthlyTurnover` |
| Для решения банка: «Гамма-Старт» | ничего из финансов |

Без полей для решения заявка после отправки придёт в `NEED_INFO` с причиной `MISSING_FIELDS` и списком в `openInfoRequest.requestedFields` — их стоит спрашивать в анкете сразу.

## Уведомления

Поток уведомлений описан в контракте как `GET /notifications/stream` (Server-Sent Events): токен — параметром `access_token`, потому что `EventSource` не умеет заголовки. Пропущенное за время обрыва — в `GET /notifications`.

## Коллекция Postman

`credit-conveyor.postman_collection.json` — 13 сценариев: шесть демо-компаний и андеррайтер (одобрение, контрпредложение, запрос сведений и отказ, подтверждение крупной суммы).

## Версии

- **0.2.0** — у фронтенда с 2026-10-22.
- **0.2.1** — уточнения без ломающих изменений: примеры с шестью демо-компаниями, как на бэкенде; `403`/`404` у операций с заявкой; `409` с `type …/concurrent-modification`; `expiresAt` в ошибке просроченного оффера; `Money` — до 15 цифр до точки; `companyId` в `PATCH` → `400`. Исправлено описание `cancel`, в примерах часовой пояс `+03:00`.
- **0.2.2** — без ломающих изменений: решение по заявке приходит асинхронно за несколько секунд после `submit` (`SUBMITTED` → `ENRICHMENT` → `SCORING` → решение); `submit` проверяет и возраст бизнеса (400); в `NEED_INFO` через `PATCH` меняются только `financials` и запрошенные поля, продукт, сумма, срок и подписка — нет (400); ответ на запрос сотрудника возвращает заявку в `MANUAL_REVIEW`, ответ при изменившихся условиях продукта — тоже (`PRODUCT_CONDITIONS_CHANGED`); в справочнике все коды причин, в том числе `PROCESSING_ERROR` (сбой обработки — ручная проверка); факторы скоринга по базовой политике (`docs/scoring.md`), новое поле `maxPoints`; в `NEED_INFO` — причина `MISSING_FIELDS`; описаны ошибки ответа на запрос и подписания (400 по полям, 404 на чужой запрос, 409 при одновременном запросе).
- **0.2.3** — без ломающих изменений, бэк-офис: в карточке `GET /backoffice/applications/{id}` новые поля `infoRequests` и `documents`, в истории — `actorName` (имя сотрудника); очередь `ALL` — без черновиков, порядок очередей описан; описаны условия ручного решения (`APPROVE` без условий — по заявке и каталогу, `COUNTER_OFFER` — с суммой, проверка по условиям продукта → 400, ставка не ниже каталога и не выше наибольшей ставки банка, до сотых, `reasonCodes` — только из справочника, оффер сотрудника не предварительный) и поля запроса сведений; `404` у решения и запроса сведений, `400` у запроса сведений; коды причин `MANUAL_REJECT` и `MANUAL_COUNTER_OFFER`; комментарий сотрудника (`comment`) виден клиенту. Уведомления: описано, о каких событиях они приходят; `POST /notifications/{id}/read` — `404` на чужое; поток SSE сразу присылает `ping`, без токена — `401`. Причины: необязательный совет клиенту `Reason.advice` (показывать отдельно от `message`). Оффер: `termKind` (`LOAN` — «500 000 ₽ на 24 месяца», `TRANCHE` — «лимит 800 000 ₽, транши до 60 дней»). Подбор: у подходящих продуктов `estimate` — предварительный платёж без подписки и с подпиской и комиссия; итоговый — в `offer`. Документы: скачивание `GET /applications/{id}/documents/{documentId}/content` и `GET /backoffice/applications/{id}/documents/{documentId}/content`, `409` у загрузки вне `NEED_INFO`, формат проверяется по содержимому, до 20 документов у заявки, `Document.infoRequestId`; в ответе на запрос нужны документы запрошенных типов (`documentIds`, иначе 400). Тексты `nextStepHint` готовы, с условиями предложения, их может уточнить PM. CORS: по умолчанию разрешены `http://localhost:5173` и `http://localhost:3000`.
