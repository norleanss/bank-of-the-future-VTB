# Умный кредитный кабинет — кредитный конвейер для МСБ

# Продукт

## 1. Коротко о продукте

- **Что:** веб-кабинет, в котором предприниматель проходит путь от «нужны деньги» до «деньги выданы», а банк ведёт ту же заявку в том же продукте.
- **Для кого:** малый и микробизнес — действующие клиенты банка, ИП и ООО. С другой стороны — андеррайтер банка.
- **Ценность для клиента:** понятный выбор продукта, никакого повторного ввода данных, статус и объяснение каждого решения.
- **Ценность для банка:** типовые заявки решаются автоматически, специалист разбирает только спорные и крупные, политика меняется без изменения кода.
- **Статус:** работающий прототип: 4 продукта, 5 исходов решения, бэк-офис, подписание и выдача.

Владельцу малого бизнеса нужен беззалоговый кредит быстро и без визита в офис — а сейчас ему приходится самому разбираться в продуктах, собирать сведения и ждать ответа без понятного статуса. Кабинет подбирает продукт под цель, сумму и срок, ведёт заявку до выдачи и объясняет каждое решение банка. Сотрудник банка получает готовую карточку с данными реестров и баллом.

В MVP — четыре беззалоговых продукта из каталога банка: кредит одной суммой, возобновляемая кредитная линия, овердрафт и «Гамма-Старт» для нового бизнеса.

- **Клиент — кабинет в браузере:** подбор продукта под потребность → заявка → прозрачный статус и уведомления → ответ на запросы банка (поля анкеты, документы) → решение → принятие условий → подписание кодом → выдача.
- **Банк — бэк-офис андеррайтера в том же интерфейсе:** проверка анкеты и условий продукта, данные из внешних источников (ЕГРЮЛ/ЕГРИП, ФНС, БКИ), скоринг и кредитная политика, решения не только «да/нет» — контрпредложение, запрос сведений, ручная проверка, подтверждение крупных сумм.

## 2. Ключевые фичи

| Фича | Что получает клиент или банк |
|---|---|
| **Подбор кредита с расчётом платежа** | Клиент отвечает на 4 вопроса (цель, сумма, срок, способ получения) и видит подходящий продукт и платёж в месяц — с подпиской и без. У каждого неподходящего продукта написано, почему он не подходит |
| **Анкета без повторного ввода** | Сумма, срок и цель приходят из подбора, ИНН и название — из профиля компании. Черновик сохраняется |
| **Личный кабинет с заявками** | Путь заявки из 7 этапов, текущий выделен; уведомления приходят без перезагрузки страницы; полная история шагов |
| **Решение не только «да» или «нет»** | 5 исходов: одобрение, другие условия, запрос сведений, ручная проверка, отказ. У каждого решения — причина простыми словами и совет, что делать дальше |
| **Рабочее место андеррайтера** | Очереди заявок, в карточке — данные ЕГРЮЛ, ФНС, БКИ и из чего сложился балл. Сотрудник видит только спорные и крупные заявки |
| **Подписание и выдача в кабинете** | Принятие условий, подписание кодом, статус «Деньги выданы» — без визита в офис |

Подробнее о каждой фиче и критериях приёмки — в разделе [7. Пользовательские истории](#7-пользовательские-истории).

## 3. Проблема

Малый бизнес — массовый сегмент: 6,6 млн компаний и ИП в реестре МСП, банки выдали им 1,313 трлн ₽ кредитов (данные кейса, июль 2026). Заявок много, они разные, и обе стороны страдают.

| | Боль | Что из этого следует |
|---|---|---|
| **Предприниматель** | Не понимает, какой кредит подходит под его задачу, — банковской экспертизы у него нет | Выбирает наугад или уходит |
| | Вводит данные, которые банк и так знает | Бросает анкету |
| | После отправки не видит, что происходит с заявкой | Звонит в банк, нервничает |
| | Отказ приходит без объяснения | Не знает, что исправить, идёт в другой банк |
| **Банк** | Данные из ЕГРЮЛ, ФНС и БКИ собираются вручную | Медленно и дорого |
| | Простая заявка занимает у специалиста столько же времени, сколько сложная | Очередь растёт, специалисты перегружены |

## 4. Пользователи и их задачи

Кейс называет целевым пользователем представителя малого бизнеса, который оформляет заявку от имени компании: собственника, гендиректора, финдиректора или бухгалтера, сотрудника, отвечающего за финансирование. Общее у них одно: **банковской экспертизы может не быть**.

| Персона | Кто это | Что важно |
|---|---|---|
| **Предприниматель** | Владелец ИП или ООО, уже клиент банка. Иногда у одного человека несколько компаний | Быстро, понятно, без визита в офис |
| **Андеррайтер** | Сотрудник банка, принимает решения по нестандартным заявкам | Видеть только то, где нужен человек, и сразу понимать почему |

### Jobs to be Done

**Предприниматель**
- Когда бизнесу нужны деньги под конкретную задачу, я хочу быстро понять, какой кредит подходит, чтобы не тратить время на сравнение продуктов.
- Когда я подаю заявку, я хочу не вводить то, что банк обо мне уже знает, чтобы закончить за несколько минут.
- Когда заявка отправлена, я хочу видеть, на каком она этапе, чтобы планировать бизнес, а не ждать звонка.
- Когда банк отказывает или предлагает другие условия, я хочу понимать причину, чтобы знать, что сделать дальше.

**Андеррайтер**
- Когда заявка попадает ко мне, я хочу сразу видеть данные всех источников и из чего сложился балл, чтобы решить за минуты.
- Когда типовая заявка проходит все проверки, я хочу, чтобы система решила сама, чтобы тратить время на сложные случаи.

## 6. Объём MVP по MoSCoW

Кейс просит выбрать реалистичный MVP и объяснить, что вошло и почему. Мы взяли самый массовый сценарий — действующий клиент берёт беззалоговый кредит — и прошли его целиком, а не сделали один этап очень глубоко.

| | Что | Статус | Почему так |
|---|---|---|---|
| **Must** | Подбор продукта под цель, сумму и срок | ✅ | Клиент без экспертизы не может выбрать сам |
| | Заявка с автозаполнением и проверкой полей | ✅ | Кейс: «сокращать повторный ввод информации» |
| | Проверки ЕГРЮЛ, ФНС, БКИ | ✅ (моки) | Без них нет оценки риска; кейс разрешает моки |
| | Скоринг и кредитная политика отдельно | ✅ | Кейс прямо разделяет оценку риска и решение |
| | Исходы кроме «да/нет»: другие условия, запрос сведений | ✅ | Кейс: итог «не обязательно бинарен» |
| | Прозрачный статус и уведомления в кабинете | ✅ | Кейс: сценарий без почты, звонков и SMS |
| | Бэк-офис андеррайтера | ✅ | Кейс: часть операций требует участия сотрудника |
| | Подписание и выдача | ✅ (смоделированы) | Без них путь не сквозной |
| **Should** | Загрузка документов в ответ на запрос банка | ✅ | Часть заявок без документов не решить |
| | Подтверждение крупных сумм сотрудником | ✅ | Контроль риска там, где ошибка дорогая |
| | Подписка: ставка ниже за пакет услуг | ✅ | Видно выгоду ещё до заявки |
| **Could** | Несколько компаний в одном профиле | ✅ | Частая ситуация у предпринимателей |
| | Адаптивный интерфейс для телефона | ✅ | Клиенту удобно проверить статус с телефона |
| **Won't (сейчас)** | Залоговые кредиты | — | Отдельный процесс с оценкой залога |
| | Новые клиенты банка и регистрация компании | — | Другой сценарий: онбординг, KYC |
| | Обслуживание после выдачи | — | Кейс заканчивается результатом по заявке |
| | Мобильное приложение | — | Запрещено условиями кейса |
| | ИИ в кредитном решении | — | См. [Почему без ИИ](#почему-без-ии) |

## 7. Пользовательские истории

Формат: «Как <кто>, я хочу <что>, чтобы <зачем>» и критерии приёмки.

**1. Подбор продукта**
Как предприниматель, я хочу ответить на несколько простых вопросов и получить подходящий кредит, чтобы не разбираться в продуктовой линейке.
- Дано: клиент вошёл в кабинет. Когда: он отвечает на 4 вопроса (цель, сумма, срок, способ получения). Тогда: видит рекомендованный продукт и платёж в месяц с подпиской и без.
- У каждого неподходящего продукта написано, почему он не подходит.

**2. Без повторного ввода**
Как предприниматель, я хочу, чтобы анкета уже знала то, что я ввёл раньше, чтобы закончить быстрее.
- Сумма, срок и цель приходят из подбора; ИНН и название — из профиля компании.
- Черновик сохраняется, к нему можно вернуться.

**3. Прозрачный статус**
Как предприниматель, я хочу видеть, где моя заявка, чтобы не звонить в банк.
- Путь из 7 этапов на странице заявки, текущий этап выделен.
- Новое событие приходит уведомлением без перезагрузки страницы.

**4. Встречное предложение**
Как предприниматель, я хочу получить доступную сумму вместо отказа, если запросил слишком много.
- Дано: запрошенная сумма больше лимита по финансам. Тогда: банк предлагает сумму лимита, клиент может принять или отказаться.
- Пример из демо: запрошено 12 млн, предложено 9,4 млн.

**5. Понятный отказ**
Как предприниматель, я хочу знать причину отказа, чтобы понимать, что исправить.
- Каждая причина — текст для клиента и, где возможно, совет. Например: «Есть просрочка больше 60 дней» → «Погасите просрочку и подайте заявку через 3 месяца».

**6. Запрос сведений**
Как предприниматель, я хочу дозаполнить недостающие данные прямо в кабинете, чтобы заявка не застряла.
- Банк указывает, каких полей или документов не хватает; клиент отвечает в кабинете; заявка уходит на повторную проверку.

**7. Работа андеррайтера**
Как андеррайтер, я хочу видеть в одной карточке данные источников и разбивку балла, чтобы решить быстро и обоснованно.
- Очереди «На рассмотрении» и «Подтверждение условий», дольше ждущие — первыми.
- Решения: одобрить, предложить другие условия, запросить сведения, отказать. При отказе и других условиях комментарий обязателен, клиент его видит.

**8. Устойчивость к сбоям**
Как банк, я хочу, чтобы сбой внешнего сервиса не терял заявку.
- Дано: ЕГРЮЛ, ФНС или БКИ не ответил после повторов. Тогда: заявка уходит специалисту с понятной клиенту причиной.

## 8. Продуктовые решения

| Решение | Почему |
|---|---|
| Подбор идёт до анкеты | У клиента нет банковской экспертизы. Вопросы «зачем и сколько» понятнее, чем витрина продуктов |
| Пять исходов вместо «да/нет» | Каждое встречное предложение и запрос сведений — клиент, которого при отказе мы бы потеряли |
| Отказ всегда с причиной и советом | Клиент знает, с чем вернуться, вместо того чтобы уйти к конкуренту |
| Автоматика до 1 000 000 ₽, выше — подтверждает сотрудник | Скорость для массовых заявок, контроль для крупных |
| Скоринг отдельно от политики, пороги в настройках | Как требует кейс. Банк меняет политику без изменения кода |
| Новому бизнесу подсказываем «Гамма-Старт» | Отказ по возрасту бизнеса превращается в другой продукт |
| Всё внутри кабинета | Условие кейса, и так проще клиенту |

### Почему без ИИ

Кейс говорит, что ИИ «приветствуется, но не обязателен», а скоринг «не обязательно представляет собой сложную ML-модель». В кредитном решении нейросеть даёт больше рисков, чем пользы, поэтому решают прозрачные правила:
- каждое решение можно объяснить клиенту и проверяющему;
- на одинаковых данных решение всегда одинаковое;
- нет затрат на модели и видеокарты, стенд работает на обычном ПК;
- данные клиентов не уходят во внешние сервисы;
- типовая заявка на демо-стенде получает решение меньше чем за секунду.

Когда появятся реальные данные, ML-модель встанет ещё одним источником балла — без изменения политики и интерфейса.

## 9. Скоринг и принятие решений

Решение по заявке принимает система по прозрачным правилам; сомнительные и крупные случаи передаются сотруднику банка. Скоринг (оценка риска) и кредитная политика (решение и условия) разделены и реализованы в модуле `scoring` бэкенда тремя компонентами без зависимостей от базы и фреймворка: `Scorer` считает балл, `CreditPolicy` принимает решение, `OfferCalculator` считает условия предложения. Все числа — баллы, пороги, лимиты — вынесены в конфигурацию `app.scoring` и меняются без правки кода. Модели машинного обучения не используются: правила детерминированные, каждое решение можно объяснить.

### 9.1. Оценка риска

Балл от 0 до 100 — сумма баллов шести факторов. Данные берутся из анкеты клиента и из ответов ЕГРЮЛ/ЕГРИП, ФНС и БКИ.

| Фактор | Что оценивает | Источник | Максимум баллов |
|---|---|---|---|
| Рентабельность | (выручка − расходы) / выручка | анкета | 25 |
| Долговая нагрузка | платежи по кредитам за год / выручка | анкета | 20 |
| Просрочка | максимальная просрочка за 12 месяцев | БКИ | 20 |
| Возраст бизнеса | месяцев с даты регистрации | ЕГРЮЛ / ЕГРИП | 15 |
| Налоговый долг | сумма задолженности | ФНС | 10 |
| Действующие кредиты | количество | БКИ | 10 |

По баллу присваивается грейд риска: A — 85–100, B — 70–84, C — 55–69, D — 40–54, E — 0–39. Для продукта без финансовых документов («Гамма-Старт») финансовые факторы не считаются, а балл нормируется по остальным.

Почему выбраны именно эти шесть факторов и такие веса — [docs/scoring.md, «Почему такие факторы и веса»](docs/scoring.md#почему-такие-факторы-и-веса).

### 9.2. Порядок принятия решения

Проверки идут сверху вниз, первая сработавшая определяет решение.

| Шаг | Условие | Решение |
|---|---|---|
| 1 | Компания не найдена в ЕГРЮЛ | **Отказ** |
| 2 | ЕГРЮЛ, ФНС или БКИ не ответили после повторных попыток | **Ручная проверка** |
| 3 | Стоп-фактор: компания ликвидируется или ликвидирована, просрочка больше 60 дней, налоговый долг больше 300 000 ₽ | **Отказ** |
| 4 | Продукт не подходит по возрасту бизнеса | **Отказ** с подсказкой, какой продукт подойдёт (например, «Гамма-Старт») |
| 5 | Не заполнены обязательные поля анкеты | **Запрос сведений** со списком полей |
| 6 | Балл ниже 40 | **Отказ** с советом |
| 7 | Балл 40–69 или мягкий фактор (просрочка 31–60 дней, убыток за год) | **Ручная проверка** |
| 8 | Лимит по финансам меньше минимальной суммы продукта | **Отказ** с советом |
| 9 | Запрошено больше лимита | **Контрпредложение** на сумму лимита |
| 10 | Иначе | **Одобрение** |

Одобрение или контрпредложение на сумму больше 1 000 000 ₽ — предварительное: после согласия клиента условия подтверждает андеррайтер.

### 9.3. Лимит и условия

| Продукт | Лимит по финансам |
|---|---|
| Кредит одной суммой, кредитная линия | годовая выручка × доля по грейду (A — 0,5; B — 0,4) − текущий долг по БКИ |
| Овердрафт | 0,5 × среднемесячный оборот по счёту |
| «Гамма-Старт» | потолок продукта — 1 000 000 ₽ |

Ставка, комиссия за подписку и срок договора — из каталога продуктов; ежемесячный платёж считается по аннуитетной формуле или как проценты за месяц, в зависимости от способа погашения. Тот же расчёт показывает примерный платёж ещё на этапе подбора продукта.

### 9.4. Объяснение решения

Каждое решение сопровождается причинами с текстом для клиента и советом, что делать дальше: например, «Есть просрочка по кредиту больше 60 дней» — «Погасите просрочку и подайте заявку снова через 3 месяца». Сотрудник банка в карточке заявки видит балл, грейд и вклад каждого фактора; клиенту балл не показывается — только понятные причины.

### 9.5. Упрощения скоринга в MVP

Веса и пороги заданы экспертно, а не обучены на истории дефолтов. Финансовые данные — со слов клиента, без отчётности и выписок; обороты по счёту не сверяются с банком; ставка не зависит от риска. Демо-данные синтетические: шесть компаний, по одной на сценарий.

Подробно — [docs/scoring.md](docs/scoring.md): полосы баллов по каждому фактору, коды причин, формулы платежа и настройки.

## 10. Метрики

Метрики устроены в три уровня: одна главная метрика, метрики по шагам пути клиента и защитные метрики. Защитные не дают улучшить скорость ценой качества кредитов.

### 10.1. Главная метрика (North Star)

**Число кредитов, выданных через кабинет за месяц.**

Она растёт, только когда продукт работает целиком: клиент нашёл подходящий продукт, подал заявку, получил решение и подписал договор. Если ломается любой шаг, главная метрика это покажет.

### 10.2. Метрики пути клиента

Идут в порядке шагов. Если главная метрика упала, по ним видно, на каком шаге теряем клиентов.

| Шаг | Метрика | Как считаем | Хорошо, если | Что показывает |
|---|---|---|---|---|
| Подбор | Конверсия подбора в заявку | Отправленные заявки / завершённые подборы | ↑ растёт | Помогает ли подбор выбрать продукт |
| Анкета | Доля брошенных анкет | Черновики, которые не отправили / все черновики | ↓ падает | Не слишком ли длинная анкета |
| Решение | Время до решения | От отправки заявки до решения банка: одобрение, другие условия или отказ | ↓ падает | Как долго клиент ждёт ответа |
| Решение | Доля автоматических решений | Решения без сотрудника / все решения | ↑ растёт | Сколько времени экономим специалистам |
| Решение | Время в очереди специалиста | Сколько заявка ждёт на рассмотрении у сотрудника | ↓ падает | Не стала ли ручная проверка узким местом |
| Предложение | Принятые встречные предложения | Принятые / все встречные предложения | ↑ растёт | Сохраняем ли клиента вместо отказа |
| Предложение | Истёкшие предложения | Одобрения без ответа клиента за 7 дней / все одобрения | ↓ падает | Устраивают ли клиента условия |
| Выдача | Конверсия заявки в выдачу | Выданные кредиты / отправленные заявки | ↑ растёт | Сколько заявок доходит до денег |
| Выдача | Время до денег | От отправки заявки до выдачи | ↓ падает | Весь путь клиента, а не только решение |
| После отказа | Возвраты после отказа | Компании, подавшие новую заявку после отказа с советом / все отказы | ↑ растёт | Работают ли наши объяснения |

### 10.3. Защитные метрики

| Метрика | Как считаем | Хорошо, если | Зачем |
|---|---|---|---|
| Просрочка по выданным кредитам | Доля кредитов с просрочкой, отдельно для автоматических и ручных одобрений | не растёт | Автоматика не должна одобрять рискованных клиентов |
| Пересмотр крупных одобрений | Доля одобрений больше 1 000 000 ₽, которые специалист при подтверждении изменил или отклонил | низкая и стабильная | Если доля растёт — пора пересмотреть пороги политики |

### 10.4. Что уже можно измерить

Прототип сохраняет каждую смену статуса заявки с временем и автором: системой, клиентом или сотрудником. Из этой истории уже сейчас считаются время до решения и до денег, доля автоматических решений, время в очереди, принятые встречные и истёкшие предложения, конверсия заявки в выдачу.

Для конверсии подбора и брошенных анкет нужно дописать сбор событий в интерфейсе. Числовые цели поставим после пилота на реальных клиентах: на синтетических данных они ничего не значат.

## 11. Развитие

### 11.1. Приоритизация (RICE)

RICE = Охват × Влияние × Уверенность / Трудозатраты. Оценки экспертные, команды: охват — доля заявителей, которых коснётся изменение (из 10), влияние — от 0,25 до 3, трудозатраты — в человеко-неделях.

| Инициатива | Охват | Влияние | Уверенность | Трудозатраты | RICE |
|---|---|---|---|---|---|
| Обороты и выписки по счёту вместо финансов в анкете | 9 | 2 | 80% | 3 | **4,8** |
| Предодобренные предложения по истории клиента | 6 | 2 | 50% | 3 | **2,0** |
| Обслуживание после выдачи: график, транши, досрочное погашение | 7 | 2 | 80% | 6 | **1,9** |
| Ставка в зависимости от риска | 8 | 1 | 50% | 4 | **1,0** |
| Залоговые продукты с оценкой залога | 3 | 3 | 50% | 8 | **0,6** |

| Сейчас | Дальше | Позже |

# Запуск и проверка

## 12. Быстрый запуск

Нужны Git и запущенный Docker Desktop (или Docker Engine) с Linux-контейнерами и Docker Compose v2+. Локальные Java, Maven и Node.js для запуска стенда не требуются. Из корня репозитория:

```sh
docker compose up -d --build --wait
docker compose ps
```

Первый запуск скачивает образы, Maven- и npm-зависимости; следующие сборки используют кэш. Готовый стенд — четыре сервиса со статусом `healthy`. Миграции базы и демо-данные создаются автоматически.

| Сервис | Адрес на компьютере | Назначение |
|---|---|---|
| Кабинет | http://127.0.0.1:5173 | веб-интерфейс клиента и сотрудника банка |
| API через Nginx | http://127.0.0.1:5173/api/v1/actuator/health/readiness | проверка всего пути до бэкенда; ответ `{"status":"UP"}` |
| API напрямую | http://localhost:8080/api/v1 | Spring Boot в отдельном контейнере |
| Swagger UI | http://localhost:8080/api/v1/swagger-ui.html | контракт API с примерами и запросы к API |
| WireMock | http://localhost:8089/__admin/health | моки внешних источников |
| PostgreSQL | `localhost:55432` | база `credit_conveyor`, пользователь и пароль `credit` |

Все порты опубликованы только на `127.0.0.1`. Если порт занят — поменяйте его в `.env` (см. [переменные окружения](#152-переменные-окружения)) и снова выполните команду запуска.

Остановка — `docker compose down` (заявки и документы сохраняются в томе `postgres-data`). Начать с исходных демо-данных:

```sh
docker compose down -v
docker compose up -d --build --wait
```

`down -v` удаляет все заявки и документы этого Compose-проекта. Если сервис не стал `healthy` — `docker compose ps` и `docker compose logs --tail=100 backend frontend`.

Ресурсы: обычный ПК, GPU не нужен, интернет — только для скачивания образов и зависимостей при первой сборке.

# Техническая часть

## 14. Архитектура

Схема компонентов, диаграмма состояний заявки (16 статусов, 32 перехода) и модель данных — **[docs/diagrams.md](docs/diagrams.md)**.

```
Браузер ──► Nginx (frontend, :5173) ──/api/v1──► backend (Spring Boot, :8080) ──► PostgreSQL
               статика React              │                                     (схема на модуль)
                                          └──HTTP──► WireMock: ЕГРЮЛ, ФНС, БКИ
```

- **Веб-интерфейс** — одно React-приложение с двумя ролями (кабинет клиента и бэк-офис). Production-сборку отдаёт Nginx; он же проксирует `/api/v1` на бэкенд, поток уведомлений (SSE) — без буферизации. Слои: `app` (маршруты, макет, общие запросы), `pages` (экраны), `features` и `entities` (анкета, решения, статусы, проверка полей на Zod), `shared` (API, моки, UI-компоненты). Все обращения к серверу идут через интерфейс `CreditApi` — HTTP-адаптер с JWT и разбором ошибок Problem Details (или имитация API в браузере для разработки без бэкенда); данные кэширует и обновляет TanStack Query. Уведомления приходят потоком SSE (`EventSource` на `/notifications/stream`): событие обновляет заявки и уведомления, на случай обрыва — опрос уведомлений раз в 10 с, заявки в обработке — раз в 2,5 с.
- **Бэкенд — модульный монолит** на Spring Boot 4.1 / Java 21 (Spring Modulith). Модули: `identity` (демо-вход, роли, компании клиента), `product` (каталог и подбор), `application` (заявки, машина состояний — единственное место смены статуса, предложения, подписание, выдача, документы), `enrichment` (ЕГРЮЛ/ФНС/БКИ с таймаутами и повторами), `scoring` (скоринг и кредитная политика — два раздельных компонента), `notification` (уведомления, SSE), `backoffice` (очереди и решения сотрудника). Модули общаются событиями с журналом в базе: после `submit` обработка идёт асинхронно и продолжается после перезапуска. Границы модулей проверяет тест.
- **База** — одна PostgreSQL, своя схема на модуль, схема меняется только миграциями Flyway.
- **Контракт API** — `docs/api/openapi.yaml`: из него генерируются интерфейсы контроллеров и DTO бэкенда, по нему работает фронтенд.
- **Безопасность** — JWT, роли клиента и сотрудника, клиент видит только заявки своих компаний; каждый переход статуса пишется в историю, недопустимый — `409`, одновременное изменение — оптимистичная блокировка.
- **Решение по заявке** — модуль `scoring`, правила описаны в разделе [9. Скоринг и принятие решений](#9-скоринг-и-принятие-решений).

При росте нагрузки модули выносятся в отдельные сервисы, события — в брокер сообщений (Kafka), не меняя логику.

### 15.2. Переменные окружения

Все необязательны — без `.env` стенд запускается со значениями по умолчанию. Чтобы изменить, скопируйте корневой `.env.example` в `.env` (`cp .env.example .env`; в PowerShell — `Copy-Item .env.example .env`).

| Переменная | По умолчанию | Что меняет |
|---|---|---|
| `FRONTEND_PORT` | `5173` | порт кабинета на компьютере |
| `BACKEND_PORT` | `8080` | порт прямого доступа к API |
| `POSTGRES_PORT` | `55432` | порт базы на компьютере; внутри сети остаётся `5432` |
| `WIREMOCK_PORT` | `8089` | порт моков на компьютере |
| `POSTGRES_DB` / `POSTGRES_USER` / `POSTGRES_PASSWORD` | `credit_conveyor` / `credit` / `credit` | параметры базы |
| `JWT_SECRET` | пусто — случайный ключ при каждом старте (после перезапуска бэкенда нужен повторный вход) | ключ подписи токенов, не короче 32 байт |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173,http://localhost:3000` | с каких адресов разрешены прямые запросы к бэкенду |
| `COMPOSE_PROJECT_NAME` | `credit-conveyor` | имя проекта Compose, префикс контейнеров и тома |

В Docker кабинет всегда работает с настоящим API по `/api/v1` через Nginx; `frontend/.env.local` и `API_PROXY_TARGET` относятся только к локальной разработке. Внутренние адреса сервисов (`backend:8080`, `postgres:5432`, `wiremock:8080`) от портов на компьютере не зависят.

## 16. Ограничения MVP

- Внешние источники (ЕГРЮЛ/ЕГРИП, ФНС, БКИ) — моки WireMock с заранее заданными ответами; данные синтетические.
- Вход без пароля по роли; подписание — кодом, который показан в кабинете; выдача моделируется сменой статуса; уведомления только в кабинете, без email и SMS.
- Ставка — из каталога, без надбавки за риск; долговая нагрузка — по платежам из анкеты, без сверки с БКИ.
- Только действующие клиенты банка — ИП и ООО: без привлечения новых клиентов, регистрации компании и физлиц без бизнеса.
- Каталог упрощён: нет залоговых версий продуктов (в исходном каталоге — до 150 млн ₽ и 10 лет) и поручительства; подписка — одна опция, «Защита бизнеса» входит в неё, комиссия за подписку — фиксированные 1% у овердрафта (в исходном каталоге 1–5% от лимита).
- Сценарий заканчивается выдачей: нет обслуживания кредита — графика платежей, выдачи и погашения траншей в рамках лимита, досрочного погашения, ежемесячного пересмотра лимита овердрафта по оборотам.

Что и в каком порядке будем развивать — [11. Развитие](#11-развитие).
