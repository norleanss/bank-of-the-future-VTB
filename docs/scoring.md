# Скоринг и кредитная политика

Базовая политика команды для MVP, утверждена командой. Основа — модель аналитика данных из её ноутбука: стоп-факторы, пороги балла 40 и 70, ручная проверка при просрочке 31–60 дней, контрпредложение. Бэкенд доработал её по документу задач DS: шкала без насыщения, шесть факторов, грейды, объяснения по каждому фактору, лимит с учётом текущих долгов, ликвидация и запрос сведений. Все числа — баллы, пороги, лимиты, граница автоодобрения — задаются в `app.scoring` (`backend/src/main/resources/application.yml`) и меняются без правки кода.

Скоринг оценивает риск и даёт балл. Политика по баллу и данным заявки принимает решение и считает условия. Оба компонента — чистые функции без базы и Spring: `Scorer`, `CreditPolicy`, `OfferCalculator` в модуле `scoring`.

## Порядок проверок

Проверки идут сверху вниз, первая сработавшая даёт решение.

| № | Условие | Решение | Причины |
|---|---|---|---|
| 1 | Компания не найдена в ЕГРЮЛ/ЕГРИП | `REJECT` | `COMPANY_NOT_FOUND` |
| 2 | ЕГРЮЛ, ФНС или БКИ не ответил после повторов | `MANUAL_REVIEW` | `SOURCE_UNAVAILABLE` |
| 3 | Есть стоп-фактор | `REJECT` | все сработавшие стоп-факторы |
| 4 | Возраст бизнеса меньше минимального для продукта | `REJECT` | `PRODUCT_NOT_ELIGIBLE` (с подсказкой про Гамма-Старт, если он подходит) |
| 5 | Не заполнены обязательные поля анкеты | `NEED_INFO` | `MISSING_FIELDS` + список полей |
| 6 | Балл < 40 | `REJECT` | `SCORE_LOW` + слабые факторы |
| 7 | Балл 40–69 или есть мягкий фактор | `MANUAL_REVIEW` | `SCORE_GREY_ZONE` и/или мягкие факторы |
| 8 | Лимит по финансам меньше минимальной суммы продукта | `REJECT` | `INSUFFICIENT_FINANCES` |
| 9 | Запрошено больше лимита | `COUNTER_OFFER` на сумму лимита | `AMOUNT_ABOVE_LIMIT` |
| 10 | Иначе | `APPROVE` на запрошенную сумму | — |

**Соответствие продукта (шаг 4).** Возраст бизнеса — полных месяцев с даты регистрации из ЕГРЮЛ на текущую дату, минимум — `minBusinessAgeMonths` продукта из каталога (кредит одной суммой и кредитная линия — 12 месяцев, овердрафт и Гамма-Старт — без ограничения). Гамма-Старт (`alternative-product`) предлагается в тексте причины, если подходит по возрасту бизнеса и запрошенной сумме. То же правило — в подборе (`POST /products/match`) и при отправке заявки (400 по дате регистрации из базы банка); в политике проверка остаётся страховкой — по данным ЕГРЮЛ.

Итоговая сумма предложения (шаги 9–10) больше **N = 1 000 000 ₽** — одобрение предварительное (`offer.preliminary = true`): после согласия клиента условия подтверждает андеррайтер. При N = 0 через андеррайтера идут все одобрения.

## Факторы скоринга

Балл — сумма баллов факторов, шкала 0–100, без обрезки. Полосы проверяются сверху вниз: первая подходящая даёт баллы.

| Фактор | Что считаем | Источник | Полосы → баллы | Макс. |
|---|---|---|---|---|
| `PROFITABILITY` | (выручка − расходы) / выручка, % | анкета | ≥ 20 → 25; ≥ 10 → 18; > 0 → 8; убыток (≤ 0) → 0 | 25 |
| `DEBT_LOAD` | платежи по кредитам × 12 / выручка, % | анкета | < 10 → 20; < 25 → 12; ≤ 40 → 4; > 40 → 0 | 20 |
| `OVERDUE_DAYS` | макс. просрочка за 12 мес., дней | БКИ | 0 → 20; 1–30 → 10; 31–60 → 0 | 20 |
| `TAX_DEBT` | налоговый долг, ₽ | ФНС | 0 → 10; до 50 000 включительно → 5; больше → 0 | 10 |
| `BUSINESS_AGE` | полных месяцев с регистрации на текущую дату | ЕГРЮЛ | ≥ 36 → 15; 12–35 → 10; 3–11 → 5; < 3 → 0 | 15 |
| `ACTIVE_CREDITS` | действующих кредитов | БКИ | 0–1 → 10; 2 → 5; 3 и больше → 0 | 10 |

Проценты округляются до сотых (половина вверх) до сравнения с полосой — в разбивке видно то же значение, по которому начислены баллы. По каждому фактору сохраняется код, входное значение, баллы и объяснение на русском («Рентабельность 30%», «Максимальная просрочка за 12 месяцев — 12 дней»).

**Без финансовых данных.** Если поля анкеты не обязательны для продукта (Гамма-Старт) и не заполнены, финансовый фактор не считается, а балл нормируется: сумма / максимум посчитанных факторов × 100, половина вверх. В разбивке появляется строка `NORMALIZATION` с поправкой, поэтому сумма баллов по факторам всегда равна итоговому баллу. Пример: 45 из 55 → 82.

## Стоп- и мягкие факторы

| Тип | Условие | Код |
|---|---|---|
| Стоп | Статус компании `LIQUIDATING` | `COMPANY_LIQUIDATING` |
| Стоп | Статус компании `LIQUIDATED` | `COMPANY_LIQUIDATED` |
| Стоп | Просрочка за 12 мес. > 60 дней | `OVERDUE_GT_60` |
| Стоп | Налоговый долг > 300 000 ₽ | `TAX_DEBT_HIGH` |
| Мягкий | Просрочка за 12 мес. 31–60 дней | `OVERDUE_31_60` |
| Мягкий | Убыток за год: расходы ≥ выручки | `LOSS_MAKING` |

Стоп-факторы проверяются до скоринга, мягкие — после: при балле < 40 решение — отказ, даже если есть мягкий фактор.

## Обязательные поля для решения

| Продукт | Поля |
|---|---|
| `LUMP_SUM_LOAN`, `CREDIT_LINE` | `financials.annualRevenue`, `financials.annualExpenses`, `financials.monthlyDebtPayment` |
| `OVERDRAFT` | то же + `financials.bankMonthlyTurnover` |
| `GAMMA_START` | нет |

Не хватает полей — `NEED_INFO`, список полей уходит в запрос клиенту (путь как в `PATCH`).

## Лимит по финансам

| Продукт | Лимит |
|---|---|
| `LUMP_SUM_LOAN`, `CREDIT_LINE` | выручка за год × доля по грейду (A — 0,5; B — 0,4) − текущий долг по БКИ |
| `OVERDRAFT` | 0,5 × среднемесячные обороты по счёту |
| `GAMMA_START` | потолок продукта (1 000 000 ₽), без финансов |

Лимит округляется вниз до 10 000 ₽, не больше потолка продукта и не меньше нуля. До расчёта лимита доходят только заявки с баллом ≥ 70 (грейды A и B); для грейда без доли в настройках лимит 0. Контрпредложение — тот же продукт и срок, сумма = лимит.

## Условия предложения

| Условие | Правило |
|---|---|
| Ставка | из каталога: с подпиской, если заявка с подпиской и у продукта есть ставка с подпиской, иначе базовая |
| Комиссия за подписку | сумма × `subscriptionFeePercent` / 100, единоразово при выдаче; сейчас только у овердрафта (1%) |
| Срок договора | из каталога (`agreementTermMonths`); у кредита одной суммой нет |
| Способ погашения | из заявки, если продукт его допускает, иначе первый способ продукта |
| Платёж `ANNUITY` | P × r / (1 − (1 + r)^−n), r — месячная ставка, n — срок в месяцах |
| Платёж `INTEREST_ONLY` | P × r — проценты за месяц при полном использовании лимита |

Месячная ставка: годовая / 12 / 100; у ставки в день (Гамма-Старт) — дневная × 30 / 100. Срок в днях переводится в месяцы с округлением вверх (месяц = 30 дней). Деньги — `BigDecimal`, округление до копеек половина вверх; комиссия в платёж не входит.

Примеры: 5 000 000 ₽ на 36 мес. под 23,5% — 194 854,03 ₽ в месяц; овердрафт 800 000 ₽ с подпиской под 13% — 8 666,67 ₽ процентов в месяц и комиссия 8 000 ₽; Гамма-Старт 500 000 ₽ с подпиской под 0,15% в день — 22 500 ₽ в месяц.

Совет клиенту — отдельное поле `advice` у причин отказа и контрпредложения (не в тексте причины); у остальных
причин и где сделать ничего нельзя (ликвидация) совета нет.

| `SOURCE_UNAVAILABLE` | шаг 2 | Внешний источник данных временно недоступен — заявку проверит специалист | — |
| `COMPANY_LIQUIDATING` | стоп-фактор | Компания находится в процессе ликвидации | — |

| `PRODUCT_NOT_ELIGIBLE` | шаг 4 | Продукт «Кредит одной суммой» доступен бизнесу от 12 месяцев | Подайте заявку на «Гамма-Старт» — он для нового бизнеса и без финансовых документов (если Гамма-Старт подходит по сумме); иначе — Подайте заявку, когда бизнесу исполнится 12 месяцев |

| `MANY_ACTIVE_CREDITS` | шаг 6, слабый фактор | Много действующих кредитов | Закройте часть действующих кредитов или объедините их рефинансированием |

| `LOSS_MAKING` | шаг 7, мягкий фактор | По данным анкеты расходы за год не меньше выручки | — |

| `MANUAL_COUNTER_OFFER` | контрпредложение сотрудника | Комментарий сотрудника | Примите предложение или откажитесь от него и подайте новую заявку на других условиях |

Слабый фактор — набравший меньше половины своего максимума (`weak-factor-share`). Числа в текстах берутся из настроек и расчёта.

|---|---|
| Полосы факторов | `factors.<фактор>.bands` (`when`: `LT`, `LE`, `GE`, `GT`; `value`; `points`), `otherwise` |
| Доля для слабого фактора | `weak-factor-share` |
| Грейды | `grades` |
| Пороги балла | `reject-below` (40), `review-below` (70) |
| Стоп-факторы | `stop-factors.company-statuses`, `max-overdue-days`, `max-tax-debt` |
| Продукт-альтернатива по возрасту бизнеса | `alternative-product` |
| Мягкие факторы | `soft-factors.overdue-days-from`, `soft-factors.loss` |
| Обязательные поля | `required-fields.<продукт>` |
| Лимит | `limits.method.<продукт>` (`REVENUE`, `TURNOVER`, `PRODUCT_MAX`), `revenue-share-by-grade`, `turnover-share`, `rounding-step` |
| Граница автоодобрения N | `preliminary-above` |

Минимальный возраст бизнеса продукта — в каталоге (`product.credit_products.min_business_age_months`), не в `app.scoring`.

Неизвестное поле в `required-fields` или лимит по полю, которое не обязательно для продукта, — ошибка при старте приложения.

## Обработка заявки

После `submit` ответ сразу — `SUBMITTED`, дальше асинхронно, через события модулей (журнал событий в базе: необработанное событие доставляется после перезапуска):

1. `SUBMITTED → ENRICHMENT`: запросы к ЕГРЮЛ, затем параллельно к ФНС и БКИ. Таймауты — подключение 1 с, чтение 2 с; при ошибке сети, таймауте или ответе 5xx — 2 повтора с паузой 0,5 с (`integrations.*`). Ответы источников сохраняются как есть.
2. ЕГРЮЛ ответил 404 → `REJECTED` (`COMPANY_NOT_FOUND`); источник не ответил после повторов → `MANUAL_REVIEW` (`SOURCE_UNAVAILABLE`) — сразу из `ENRICHMENT`, без скоринга.
3. Иначе `ENRICHMENT → SCORING` и решение политики; балл с разбивкой и решение сохраняются. Все переходы — от имени системы.
4. `NEED_INFO`: клиенту уходит запрос со списком полей. Через `PATCH` меняются только эти поля и финансы, продукт, сумма, срок и подписка — нет. При ответе требуется, чтобы запрошенные поля были заполнены (иначе 400). Если за это время изменились условия продукта (продукт снят, сумма или срок вне условий) — исправить это клиент не может, заявка уходит в `MANUAL_REVIEW` с причиной `PRODUCT_CONDITIONS_CHANGED`. Иначе после ответа на запрос системы заявка проходит шаги 1–3 заново (новый круг; события прежнего круга игнорируются), на запрос андеррайтера — возвращается к нему (`MANUAL_REVIEW`).
5. После согласия клиента — код подписания (5 минут, 3 попытки, `app.signing.*`) → `SIGNED` → система моделирует выдачу → `DISBURSED`.
6. Непредвиденная ошибка обработки (например, продукт убрали из каталога) — заявка в отдельной транзакции уходит в `MANUAL_REVIEW` с причиной `PROCESSING_ERROR`, подробности — в логе. Ошибка в событии прежнего круга и конфликт версий (одно событие обработано дважды) сбоем не считаются. Повторно доставленное событие (после перезапуска) заявку не меняет.

### Сценарии с андеррайтером

Вход андеррайтера — `POST /auth/demo-login` с ролью `UNDERWRITER`; очереди — `GET /backoffice/applications?queue=REVIEW` и `queue=CONFIRMATION`, карточка — `GET /backoffice/applications/{id}` (анкета, ЕГРЮЛ/ФНС/БКИ, балл с разбивкой, причины, история, запросы сведений, документы).

| Шаг | Кто | Действие | Результат |
|---|---|---|---|
| **Морозов → одобрение сотрудником** | | | |
| 1 | клиент | Морозов: кредитная линия 1 000 000, как в таблице выше, `submit` | `MANUAL_REVIEW` (`OVERDUE_31_60`), заявка в очереди `REVIEW`; уведомление «Заявка на рассмотрении у специалиста» |
| 2 (по желанию) | андеррайтер | `POST …/info-requests`: «Пришлите бухгалтерскую отчётность», `requestedDocuments: [FINANCIAL_STATEMENT]` | `NEED_INFO`; клиент загружает PDF (`POST /applications/{id}/documents`) и отвечает с `documentIds` → снова `MANUAL_REVIEW` |
| 3 | андеррайтер | `POST …/decision` `{"decision": "APPROVE"}` (без условий — сумма и срок из заявки, ставка каталога; можно указать `amount`, `term`, `rate` в пределах продукта) | `APPROVED`, оффер не предварительный: «Одобрен лимит 1 000 000 ₽, транши до 6 месяцев»; в истории — имя сотрудника |
| 4 | клиент | Принять → код → подтвердить | `OFFER_ACCEPTED` → `SIGNED` → `DISBURSED` |
| **ТехноПром → подтверждение крупной суммы** | | | |
| 1 | клиент | ТехноПром: кредит одной суммой 5 000 000, 36 мес., как в таблице выше, `submit` | `APPROVED`, предварительное (5 000 000 > N = 1 000 000) |
| 2 | клиент | Принять предложение | `PENDING_CONFIRMATION`, заявка в очереди `CONFIRMATION` |
| 3 | андеррайтер | `POST …/decision` `{"decision": "APPROVE"}` (условия не передаются) | `OFFER_ACCEPTED`; клиенту — «Условия подтверждены» |
| 4 | клиент | Код → подтвердить | `SIGNED` → `DISBURSED` |

Другие решения андеррайтера: `COUNTER_OFFER` (обязательны `amount` и `comment`, можно другой продукт) и `REJECT` (обязателен `comment`) — клиент видит комментарий в причине (`MANUAL_COUNTER_OFFER`, `MANUAL_REJECT`) и совет. Условия вне продукта (сумма больше потолка, срок длиннее допустимого, ставка ниже каталога) → 400 по полю.

## Известные упрощения

| Что | Как в MVP |
|---|---|
| Долговая нагрузка | по ежемесячным платежам, которые указал клиент в анкете; без сверки с БКИ и без платежа по новому кредиту |
| Ставка | из каталога, без надбавки за риск по грейду |
